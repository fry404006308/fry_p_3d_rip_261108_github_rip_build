# 平台上线、工艺边界与回退

上线时以作业为单位保存输入 GLB 的哈希、交付号、运行时版本及指纹、OS/架构、原始请求 JSON 和输出元数据。worker 用独立目录执行，每项作业验证返回码、连续层号、层数和设备宽度后，再向打印队列登记成功。

|场景|处理|
|---|---|
|首次接入|运行根目录的 check_install.py；它调用各端原包的自检和一份已知答案，再检查一条非法请求。|
|产品包升级|将新包解压到独立目录。校对 ZIP 的 SHA256 和 PRODUCT.json，重复已知答案及业务模型测试，成功后将新作业路由到该目录。|
|宽度超出 128 喷孔|报告原生宽度，调整模型尺寸或方向，再生成新的作业。16.851 mm 测试半球实际 131 列；同一摆放改 16.0 mm 原生 125 列，可右补空至 128 列、输出 809 层。|
|重复请求或取消|使用新的任务输出目录。保留取消信息和诊断日志，隔离未完成的切片。|
|服务并发|单库实例串行提交。每任务设置 threads；按 CPU 和内存预算调度多个隔离进程。|
|跨系统复查|按架构及运行时建立基准。已有 45° HE510 半球在 Windows/Linux 出现 29 个不同材料格，详情见验收报告。|
|回退|用记录的产品 ZIP、运行时指纹和输入参数重建旧任务。先核对随包小件，再比对该业务模型。|

## 维护方更新源码后怎样重出

1. 在私有加网打包仓运行 `python tools/fry_payload.py status --source <算法仓根目录>`。另查头文件、参数协议和 CLI 的变化，这些会影响调用方。
2. 用打包仓的 `tools/fry_oneclick_release.bat` 或工作台 **HS100 打包水转印加网 SDK** 走版本判定、载荷同步、构建、平台包与本地验收。
3. 用公开二进制验收仓的 `fry_gh_publish.bat` 或工作台 **HS500 GitHub 多平台验收**，验证五种目标。发布者保存 manifest、verdict、golden 和交付件哈希。历史版本使用独立的日期时间目录。
4. 若仅更新产品资料和目录，校对库/CLI SHA 与上一受验批次。若算法或 ABI 改动，则更新运行时版本、对应的参数表和各平台 golden。
5. 将已验收件装入新产品目录，执行包内验收，再对最终 ZIP 测试。维护方将原始压缩包留在历史目录用于回退。

原始 SDK 许可随完整平台目录及产品根一并提供。外部用户能否下载原生库，应按权利人的授权范围办理。[许可](../LICENSE.txt)

本版保留原轴的请求与旧版迁移见 [原始朝向](orientation.md)。
